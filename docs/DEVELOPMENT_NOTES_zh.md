# 显微图像智能分割与定量测量工作台

零样本（Grounding-DINO + SAM）与少样本（PerSAM 式 in-context 匹配 + SAM）双模式显微图像分割、形态参数测量与报告导出的 Streamlit 工作台。

## 架构

两种识别模式只负责产出 `DetectionPrompt`（points/boxes），分割统一由同一个 `SamSegmenter` 完成：


## 关键技术结论（M0/M1 真实数据验证）

用 8 个公开数据集（详见 [`data/datasets/SOURCES.md`](../data/datasets/SOURCES.md)）做的量化验证，得到以下结论：

### 零样本模式（Grounding-DINO）—— 仅作粗筛，不作为主力检测

- **SEM/金相显微图像**：完全失效。不论提示词、阈值（试到0.15）怎么调，模型总是把整张图识别成一个目标，没有实例级定位能力。
- **宏观近距照片**（如路面/墙体裂纹）：定位精度有提升但仍不可靠，IoU 量级在 0.06~0.07，本质是把"视觉上明显不同的一大片区域"当成目标，不是精确勾勒边界。
- 结论：零样本在这类致密纹理图像上的角色应该是"有没有疑似目标"的粗筛，不能用于精确分割或定量测量。

### 少样本模式（PerSAM 式 point-matching）—— 主力方案，覆盖颗粒/气孔/晶粒/裂纹

- **团块/区域状目标**（颗粒、气孔、晶粒）：效果好。单参考图 IoU 约 0.38～0.56，**3 张参考图能显著提升**（同一案例从 0.38 提到 0.79），验证了"至少用 3 张参考图"应作为产品默认引导。
- **细长目标（裂纹）**：不是天生失效，关键变量是**背景是否均匀**——
  - 裂纹穿过多种差异很大的背景纹理（如宏观照片里路面/瓷砖）：参考特征被稀释，IoU 只有 0.028，失败。
  - 裂纹在背景材料纹理均匀一致的真实显微图像中（如水泥基复合材料微裂纹数据集）：**IoU 普遍在 0.3~0.7**，多组测试稳定。
  - **多点采样（NMS，`num_positive_points` 默认 5）对"单点在裂纹分叉处提前终止导致欠分割"这类失败有显著修复效果**：同一失败案例从 IoU=0.013 提升到 0.42~0.52（30 倍以上）。
  - 因此**裂纹类别不需要独立于少样本框架之外的检测方案**；Frangi 脊状滤波仍可作为交叉验证/备选手段保留，但不再是必需路径。
- **跨域泛化**：验证过完全陌生的领域（生物组织 H&E 病理切片，与训练/其它测试样本的材料域毫无关系），只要参考图和目标图属于**同一类样本/组织**，少样本方法依然可靠（IoU 0.71~0.79）；跨越差异很大的组织/样本类型会失败，这与真实使用场景（用户不会拿甲材料的参考图去测乙材料）是吻合的。

### 穷举检测（密集颗粒场景）—— 已探索三条路线，均未跑通，暂缓

- **动机**：真实 TiO2/silica 纳米颗粒 SEM 图像测试暴露了现有少样本架构的一个设计局限——`FewShotDetector.detect()` 每次调用只返回**一个**最佳匹配区域（多点 NMS 采样出的几个点最终会被 SAM 合并成一个 mask），不是"找出图里所有跟参考图相似的实例"。这跟密集颗粒场景（一张图里几十上百颗同类颗粒）的"自动计算所有颗粒形态参数"预期不匹配。
- **验证过的三条路线**（均用 `BAM_TiO2/prepared/images/1908267.tif`，29 颗真实颗粒 GT 作为测试用例）：
  1. **`SamAutomaticMaskGenerator`（SAM 自带"分割一切"）**：单图耗时 132~292 秒（CPU, vit_b），候选 mask 里背景明暗纹理和真实颗粒数量级相当，候选质量本身就不可靠。
  2. **网格切图 + 逐格单目标检测**：**实现思路有根本性错误，已放弃**。SAM 的图像编码器不论输入多大，内部都会先等比缩放到长边 1024px 再过 ViT-B backbone——切成小图完全不省算力，反而因为切格数量多，总开销比处理整张图贵了近百倍（96 格 × 每格 2 次全分辨率编码，实测跑 80 分钟没跑完，中途终止）。
  3. **编码一次 + 相似度热力图多峰值 + 复用编码各自解码**：架构上是对的方向——SAM 的编码器贵（整图一次 ~9.5秒）、解码器便宜（复用同一份编码，每次点提示解码只要 ~0.1秒），整图端到端约 17 秒，**速度验证通过**。但**检测质量不过关**：80 个候选峰值里只有 11 个通过可靠性校验，去重后 7 个最终检测，**对 29 颗真实颗粒的召回率只有约 10%（3/29）**，且大部分检测落在背景纹理而非真实颗粒上。
- **根因**：诊断相似度热力图发现，**真实颗粒的相似度分数（0.32~0.97）和背景纹理的相似度分数（0.19~0.97，均值0.64）区间几乎完全重叠**，背景个别斑块的相似度甚至高于部分真实颗粒——任何固定阈值都无法在这张图上干净分开两者。这不是某条实现路线的 bug，而是"用余弦相似度做逐实例穷举分类"这个思路本身在背景纹理复杂、颗粒又小（中位数直径约25px，只占 SAM 64×64 特征图的 1~2 个格子，特征已与周围背景严重混叠）的图像上站不住脚——跟已知的"稀疏背景导致误匹配到噪声"是同一类根本问题，穷举模式把它放大了：单目标模式只需要一次"最相似的恰好是颗粒"的运气，穷举模式却要求每一个高相似度峰值都是颗粒。
- **结论 / 现状**：暂缓这个方向的投入，不再是本次探索的优先级。密集颗粒场景目前的建议路径：少样本单目标模式（配合 3 张参考图，已验证能显著提升匹配质量）定位到大致区域后，配合 M5（网页端手动涂抹/擦除修正 mask，已实现，见下）让用户手动圈出其余实例。

#### 后续尝试：训练轻量分类头替代固定相似度阈值

- **动机**：上面的根因分析指出，真实颗粒和背景纹理的余弦相似度区间几乎完全重叠，单靠相似度阈值分不开两者。既然如此，在 SAM 冻结特征上训练一个小分类器（不训练 SAM 本身，只训练一个后接的判别头）去学"这个位置像不像颗粒"，原则上应该比固定阈值更准。
- **数据**：`scripts/build_particle_classifier_dataset.py` 从有实例级标注的数据集提取 grid-cell 级别的正/负样本（64×64 特征网格，和 `FewShotDetector` 的相似度热力图同一分辨率）。第一版只用 `BAM_TiO2/train.txt`（32 张 SEM 图，5.1 万样本）；第二版加入 `EMPS/train.txt` 随机抽样 60 张（共 92 图，20.5 万样本），引入不同材料/成像模态的多样性。`scripts/train_particle_classifier.py` 用 numpy 手写逻辑回归（不引入新依赖），按图片分 train/val 避免同图特征泄漏。
- **评估教训：单张测试图不可信，必须多图平均**——第一轮只用 `1908267.tif` 一张图测试，扩充数据后这张图的召回率/精确率反而**下降**了（回顾：7/29→5/29 召回，33%→19% 精确率），一度以为数据扩充没用甚至有反效果。改成在 `BAM_TiO2/test.txt` 的 8 张官方留出 SEM 图 + `1908267.tif` 共 9 张图上跑评估后才发现：**`1908267.tif` 是这 9 张里表现最差的一张**，而且是唯一一张 TSEM 图（训练数据的 BAM_TiO2 部分只用了 SEM 的 `train.txt`）——分类器在没见过的成像模式上明显打折扣，不是数据扩充本身没用。9 图平均：**召回率 24.5%（4%~54%）、精确率 63.2%（19%~89%，TSEM 图拖累了下限）**。
- **现状判断（v1）**：精确率在同域（SEM）数据上已经基本可用（多数图 68%~89%），**召回率是当前短板**（四分之三真实颗粒漏检）。识别出三个待验证的优化方向：(a) 把余弦相似度作为分类器的输入特征之一，而不是外部 AND 阈值；(b) 逻辑回归换成小 MLP；(c) 训练数据补齐 TSEM 等未见成像模式。

#### v2：针对召回率，同时验证 (a)(c) 两个方向 + 穷举模式下测试 3 参考图

- **改动**：① 特征维度从 256 扩到 257——新增一维是该 grid cell 对某个自参考颗粒的余弦相似度，训练时为每张图自选一个代表性颗粒当参考算这一维，推理时这一维直接复用 `FewShotDetector` 已经算好的相似度热力图，不增加额外开销；分类器自己学相似度和"像不像颗粒"的组合边界，取代之前 `sim≥0.6 AND clf≥0.5` 的硬阈值。② 训练集加入 BAM_TiO2 的 35 张 TSEM 图（40张里留 5 张，含 `1908267.tif`，专门做留出评估，不参与训练）。③ 穷举检测的自参考从 1 张改成 3 张（覆小/中/大三个尺寸百分位），复用单目标模式"3 张参考图显著提升匹配质量"的已验证结论。三个改动一起验证，未逐一消融。
- **评估**：`BAM_TiO2/test.txt` 8 张官方留出 SEM 图 + 5 张 TSEM 留出图（`1908267/1908277/1908287/1908297/1908307`），按域分别统计：

  | | 召回率 | 精确率 |
  |---|---|---|
  | v1（1参考图 + 硬阈值AND门，训练集仅SEM+EMPS，9图/仅TSEM混SEM未分域） | 24.5% | 63.2% |
  | v2 SEM（8图） | 32.5% | 68.0% |
  | v2 TSEM（5图） | **33.1%** | **75.6%** |
  | v2 总体（13图） | 32.7% | 71.0% |

  召回率、精确率同时提升，且**之前拖后腿的 TSEM 域反超了 SEM**（v1 里 `1908267.tif` 精确率只有 19%，是全场最差）——证实 TSEM 域外泛化差主要是训练数据没覆盖到，不是方法本身的问题。`1908267.tif` 单独看：召回率 17%→28%，精确率仍是 13 张里最低的 19%（其余 TSEM 图都在 70%+），这张图本身可能有其它因素（比如参考颗粒选取更困难），还没深挖。
- **现状判断（v2）**：召回率还是明显短板（约三分之二真实颗粒漏检），但已经不是"完全不可用"的状态。还没验证的方向：逻辑回归换小 MLP（(b) 未测）、两阶段级联用解码后的形状特征二次筛选、更合理的峰值选择策略（现在贪心 NMS 比较粗糙）。
- **产物**：`models/particle_classifier.npz`（v2 权重，257维输入，覆盖v1）、`data/datasets/particle_classifier_train.npz`（268K样本特征缓存，未纳入版本库）。

#### 已接入 app.py

`FewShotDetector.detect_all()` + `SamSegmenter.decode_point()`（core/detectors/few_shot.py、core/segmentation/sam_wrapper.py）把上面验证的流程（编码一次 -> 分类器打分找多峰值 -> 复用编码逐个解码 -> 可靠性过滤 -> IoU去重）封装成正式方法。少样本模式第二步新增"穷举检测"勾选框——`app.py` 启动时若 `models/particle_classifier.npz` 不存在会自动隐藏该选项并提示需要先跑训练脚本，不会报错。UI 文案如实标注了当前召回率/精确率水平，不包装成"已解决"。

验证方式：① `streamlit.testing.v1.AppTest` 确认零样本/少样本两种模式默认路径和模式切换都不抛异常；② 用真实图像（`1908312.tif`）直接调用 `detect_all()`（绕过 Streamlit，测底层逻辑本身）：71个候选 vs 63颗真值，召回率56%——比同一张图在独立评估脚本里的41%还好，因为 `detect_all()` 复用了 `detect()` 已有的峰值间距启发式（`max(10, min(h,w)//30)`），比原型脚本里写死的常量12更合理；③ 真实 Streamlit 页面里确认了模式切换、少样本第一步 UI 正常渲染无报错——文件上传这个具体交互目前工具链没法在浏览器里模拟真实的文件选择弹窗，没有做完整点击上传的端到端浏览器验证，但上传控件本身和现有单目标模式共用同一段代码，不是新写的。

#### 过分割排查 + `multimask_output=True` 修复

- **动机**：用户提问"是否存在目标级严重过分割"——之前报告的精确率/召回率口径有盲区：只要检测跟某个GT颗粒重叠>25%就算命中，不检查这个GT颗粒是不是已经被别的检测重复认领，过分割会被这套指标隐藏。专门写脚本按"每颗GT颗粒被几个检测认领"重新统计（13图，2112颗真值）：
  - **过分割（1颗被拆成≥2个检测）**：31颗，占全部真值的 **1.5%**——比例很低，不是主要问题
  - **误检（检测跟任何GT颗粒都对不上）**：231个，占全部检测数的 **27.6%**——这才是当前更大的问题
  - 抽查了一个被拆4份的案例（`1908326.tif` 的316号颗粒）：面积4739px²，等效直径约78px，远大于颗粒中位数（约500px²/25px）——过分割集中发生在偏大/不规则颗粒上，机制是这类颗粒跨多个特征网格格子、内部纹理有起伏，容易产生多个相隔较远的独立峰值，且 SAM 对不规则大颗粒的单点解码结果不稳定（不同起点解出不同局部），现有 IoU 去重抓不住"同一颗粒的两个不太重叠的局部"这种情况。
- **改动**：`SamSegmenter.decode_point()` 从 `multimask_output=False`（强制单一输出）改成 `multimask_output=True` 后选 SAM 自己预测IoU最高的那个候选（SAM 单点解码本来就会给3个不同粒度的候选，强制单输出经常被迫要一个不上不下的结果）。
- **效果**（同一批13图重新测）：

  | | 召回率 | 精确率（1-误检率） |
  |---|---|---|
  | 改动前 | 26.8% | 72.4%（27.6%误检） |
  | **改动后** | 27.1%（基本不变） | **88.2%（11.8%误检）** |

  精确率大幅提升，召回率完全没受影响，**纯收益**。**过分割比例没变（1.5%→1.6%）**——在预料之中，这个改动解决的是"单次解码该出整体还是局部"的粒度问题，跟"多个峰值落在同一颗粒上"是两个独立的失败模式，此方法只解决前者。真要治过分割，需要把去重逻辑从"两两比较IoU"换成"连通聚类后取并集"，还没做。
- **裂纹场景的教训（未采纳的方向）**：用户曾提议给裂纹这类细长目标做"mask合并/连接"和"减少采样点+提高NMS距离"两种后处理。实测发现前提不成立——`detect_all()`/分类器只在颗粒（团块状）正样本上训练过，从没见过裂纹（细长）形态；在 `DenseCrack` 测试图上实测，13个候选里9个跟裂纹完全不重叠（纯误检，置信度还不低），真正落在裂纹上的候选加起来只覆盖裂纹面积的3.1%——不是"裂纹被切碎成小段需要拼接"，是分类器根本不认识细长目标。这两个后处理方法都无法解决"识别不出"的问题，真要支持裂纹需要往训练数据里加裂纹正样本，从根上让分类器认识细长形态，不是后处理能修的。裂纹场景本身在单目标模式（`detect()`）下已验证良好（IoU 0.3~0.7），是否真的需要穷举模式支持裂纹还没确认。

#### 真实用户测试发现的问题："识别出来的是环绕在物体周围的"（mask 带洞），已修复

- **现象**：用户反馈另一份真实报告（`1908250.tif`）里有个检测是一个环形色块，真正的颗粒（图像里的亮斑）反而在环中间没上色——不是位置错了，是这个检测的mask本身中间破了个洞。
- **复现与根因**：在报告标注的大致位置附近扫描了一圈候选点，直接用 `SamSegmenter._predictor.predict(multimask_output=True)` 检查全部3个候选（不只是被选中的那个），发现对这一片区域（颗粒本身有明显的SEM成像亮边），**SAM 自己预测IoU最高的候选本身就是一个环**（洞占填补后面积的20%~24%），而且不是单个点的偶然结果——邻近一圈候选点全部复现了同样的现象。`decode_point()`/`decode_box()` 的"选SAM自己预测IoU最高的候选"这个逻辑（`过分割排查`那次加的）默认信任SAM自己的置信度，但SAM的置信度本身可能被这类局部亮边误导，选出一个"形状看起来自洽但语义不对"的环。
- **修复**：新增 `core/segmentation/sam_wrapper.py::_fill_holes()`（`scipy.ndimage.binary_fill_holes`），统一套在 `decode_point()`/`decode_box()`/`segment()` 三处SAM输出上——这个app要分割的目标（颗粒/晶粒/裂纹）从物理上讲都是实心的，不会是环形，mask 中间有洞只可能是SAM的伪影，不是需要保留的真实特征；正常检测本来就没有洞，套这个后处理是无操作，不会有副作用。
- **验证**：用真实数据里复现出环形的6个候选点，逐一走完整的 `decode_point()` 调用链确认洞被补上（`binary_fill_holes` 再处理一次结果不再变化，确认真的没洞了）；额外可视化了其中一个案例的修复前后效果图，确认补洞后的形状完整覆盖了图像里真正的颗粒轮廓，不是随便填了一块不相关的区域。

#### 逻辑回归换成小 MLP

- **动机**：v2 报告里识别出的待验证方向之一——线性分类器（逻辑回归）可能是精确率/召回率的天花板之一。
- **改动**：`scripts/train_particle_classifier.py` 换成 1 隐藏层 MLP（257 -> 64 ReLU -> 1 sigmoid），纯 numpy 手写前向/反向传播 + Adam，不引入新依赖；`core/detectors/particle_classifier.py` 的 `ParticleClassifier` 同步改成两层前向推理。逻辑回归权重备份在 `models/particle_classifier_logreg_backup.npz`。
- **效果**：验证集（grid-cell级别）precision 78.5%→83.4%、recall 81.6%→85.1%。同一批13图端到端评估（在 `multimask_output=True` 改动之上）：

  | | 召回率 | 精确率 |
  |---|---|---|
  | 逻辑回归 + multimask_output=True | 27.1% | 88.2% |
  | **MLP + multimask_output=True** | **29.4%** | **91.7%** |

  两个指标都提升，但召回率只涨了2.3个百分点——验证集上85%的召回率没能传导到端到端流程，说明分类器本身变强了，但流水线里还有其它环节在拖后腿（峰值选择策略、64×64网格分辨率限制等），不是换分类器就能把召回率从27%拉到85%。过分割比例不变（1.6%），符合预期（这个改动跟过分割是两回事）。
- **现状判断**：召回率仍是主要短板（约七成真实颗粒漏检）。剩下待验证方向：峰值选择策略优化（现在的贪心NMS比较粗糙，考虑高斯平滑/分水岭找局部极大值）、两阶段级联（解码后用形状特征二次筛选，让第一级可以放宽阈值多召回）、去重逻辑换成连通聚类取并集（治过分割）、评估口径改成严格一对一匹配（现在的"重叠>25%"和"中心点覆盖"都偏宽松）。

#### 峰值选择策略优化 —— 两次尝试均失败，已回滚

- **尝试1：高斯平滑 clf_prob 再找峰**——动机是网格逐格独立分类、没有空间上下文，噪声大。结果**召回率从29.4%暴跌到8.6%**：大多数颗粒只占1~2个网格格子，周围被背景格子包围，平滑会把孤立颗粒的峰值往下拉，拉到阈值以下直接被滤掉——平滑"降噪"的同时把真信号也一起抹掉了，这是"先平滑再阈值"的经典陷阱。
- **尝试2：去掉平滑，只把手写的贪心argmax循环换成 `skimage.feature.peak_local_max`**（更规范的局部极大值检测算法）——**召回率仍降到15.9%**（精确率88.7%，也没涨）。原因：`peak_local_max` 要求候选点严格大于邻域内所有其它点才算峰值，但这里的 clf_prob 网格本身很"块状"（64×64的粗网格，很多格子的分类概率彼此接近，构成大片高原而非尖锐单峰）——大量这种"高原"在严格局部极大值定义下要么整体被判定不算峰、要么只留下一个格子，而原来那个贪心版本（每次取全局最大值、以其为中心抹掉一个半径内的区域、重复）对这种大片高原反而更宽容，能从同一片高原里挖出多个分开的候选。
- **结论**：两次"更规范"的改法都比原来手写的贪心版本差，**已回滚到原实现**（`core/detectors/few_shot.py` 的 `detect_all()`）。这条方向暂时没有更好的思路——真正的问题可能不在"怎么找峰"，而在"64×64网格分辨率对1~2格大小的颗粒来说本来就太粗"，这是架构层面的限制，不是peak-finding算法能解决的。

#### 评估口径改成严格一对一匹配 —— 之前的精确率被高估了

- **动机**：之前所有轮次的评估（v1/v2/multimask_output/MLP）用的都是宽松口径——"检测覆盖GT中心点就算召回命中"、"检测跟某GT重叠>25%就算精确率命中"——都不要求一个GT只能被一个检测认领，过分割排查那轮已经发现这套口径会掩盖过分割。改成标准目标检测常用的评估方式：每个检测跟每个GT算IoU，用匈牙利算法（`scipy.optimize.linear_sum_assignment`）做最优一对一匹配，IoU≥0.5才算命中。
- **结果**（同一批13图，MLP + multimask_output=True，代码没有任何变化，只是换了评估脚本）：

  | | 召回率 | 精确率 |
  |---|---|---|
  | 宽松口径 | 29.4% | 91.7% |
  | **严格一对一匹配（IoU≥0.5）** | 25.2% | **73.8%** |

  精确率掉了18个百分点，比召回率降幅（4.2个百分点）大得多——说明宽松口径主要是在精确率上"放水"：不少检测只是勉强蹭到某颗粒边缘（超过25%但远不到50% IoU），或者好几个检测在抢同一颗真实颗粒的功劳，都被当成了独立的"正确"。**好消息**：真正匹配上的检测平均 IoU 有 0.831，说明一旦命中，分割质量本身是扎实的，问题不在分割精度，还是在"有没有找到"这个环节。
- **现状判断**：这是从现在起的标准评估口径，之前几轮报告的精确率数字（88%~92%）应该按这次的结果打折看待——各轮改动之间的**相对**提升趋势仍然可信（因为每轮都是用同一套口径做前后对比），但**绝对**数值偏乐观。真实水平是召回率约25%、精确率约74%。`app.py` 里的UI文案已同步更新为这版数字。

### 噪点过滤（`core/measurement.py`）—— 绝对阈值在跨尺度数据集上会失效

- **动机**：真实 TiO2/silica 纳米颗粒 SEM 图像测试中，原来固定的 `min_area_px=25`（绝对像素阈值）挡不住 25~40px 的噪声碎片——因为这批图像的真实颗粒本身有几千到几万像素，25px 在这个尺度下仍然是噪声，而不是小颗粒。
- **方案**：新增 `min_area_ratio=0.05` 相对阈值，`area_floor = max(min_area_px, min_area_ratio * 该mask内最大连通域面积)`，让噪声阈值跟着每张图自己的颗粒尺度自适应，而不是用一个在别的数据集上标定好的固定像素数。已用合成复现用例（大颗粒簇+噪声碎片）和两个既有回归用例验证，行为符合预期。

### 尺度标定（`core/scale.py`）—— 未标定时不再把像素值标成微米

- **修掉的问题**：之前 `compute_particle_properties()` 默认 `pixel_size_um=1.0`，却仍把列命名为 `area_um2` / `perimeter_um` / `equivalent_diameter_um`，`report.py` 还写死了"(µm)"——没有标定时，**像素值被当成微米输出**，CSV 和报告里一眼看不出来。只改标签是治标，所以这次让**单位跟着数据走**：单位直接写进列名（未标定 `area_px2` / `perimeter_px` / `equivalent_diameter_px`，标定后 `*_um` / `*_um2`，质心恒为 `centroid_px`），CSV 即使被单独打开也不会有歧义。
- **用法**：侧边栏"尺度标定"设默认尺度，每张图的测量区还有"此图尺度"可单独覆盖（同一批图放大倍数可能不同，一个默认值静默套到所有图上本身就是一种单位错误）。三种换算方式：①直接输入 µm/px；②按标尺长度换算（标尺像素长度 + 实际长度 + nm/µm/mm，像素长度可在图上沿标尺拖拽自动测得）；③按视野宽度换算（SEM 信息栏常标注，如 `Width = 7.520 µm`，仅限未裁剪未缩放的整幅图）。未标定是一等状态：全程按像素输出，不会悄悄退回 1.0 µm/px；输入 0/负数/空值时给出警告并按未标定处理。
- **传播范围**：测量表、汇总指标和直方图坐标轴的单位；CSV 每行附带 `scale_um_per_px` 和 `scale_source`（尺度来源，未标定时前者为空）；Word 报告写明尺度来源，未标定时明确声明"所有长度以像素为单位"。数值改用 4 位有效数字显示（`format_value`），因为标定后同一个量可能是 40 px 也可能是 0.18 µm，固定小数位会把 0.012 µm 的标准差显示成 0.01。
- **验证（真实数据，不是只看单位标签）**：①直径已知的合成圆盘（80 px 直径 @ 0.02 µm/px，真值 1.6 µm）测得 1.5978 µm（误差 0.13%）；标定值与像素值逐项严格满足"面积×s²、周长/直径×s"。②`BAM_TiO2/1908312.tif` 的信息栏给出两个互相独立的参照：视野宽度 `Width = 7.520 µm`（1024 px → 0.007344 µm/px）和画面自带的 200 nm 标尺。标尺**两端竖线中心到中心 27 px** → 与视野宽度换算相差 +0.87%；但**外沿到外沿 29 px** 则相差 −6.1%——**同一根短标尺，读法不同就差 7%**，所以界面里把"按视野宽度换算"作为首选并在文案里提示标尺越长越准。③真实浏览器端到端（上传真实图 → 51 个实例）：视野宽度换算（0.2462 µm）、侧边栏直接输入（0.2462 µm）和图上拖拽标尺（27.1 px = 200 nm → 0.2475 µm，相差 0.5%）三条路径互相吻合；导出的 CSV、Word 报告里尺度来源与单位一致。
- **真实浏览器测试发现并修掉的缺陷**：拖拽测量组件默认按**原始尺寸**绘图并被列宽裁剪——1024 px 的图放在约 414 px 的列里，标尺（x≈890–917）直接在可视区之外，工具根本用不了；改成 `width="stretch"` 按列宽缩放。另外校验函数最初拒收 numpy 整数（`isinstance(value, (int, float))`），而从图像读出的像素长度恰好是 `np.int64`，改用 `numbers.Real` 并显式排除 `bool`。
- **已知局限**：拖拽测量的精度取决于图像在页面上的显示倍率（窄列下 1 个屏幕像素 ≈ 1.9 个图像像素），界面会在每次拖拽后如实显示当前精度；短标尺（约 27 px）本身 ±1 px 就是 ±3.7%，能读到视野宽度时应优先用它。测量结果仍受分割质量、边界锯齿和分辨率影响，标定只负责像素到物理单位的换算，不改善分割本身。

### 裂纹测量（`core/measurement.py::compute_crack_properties`）—— 等效直径对细长目标没有物理意义

- **动机**：颗粒用的"等效直径"是按面积换算成圆的直径（√(4·面积/π)）。裂纹是细长目标，这个数既不是长度也不是宽度，标定成 µm 后看起来像一个真实尺寸，其实没有意义；"粒径分布""圆度"同理。所以"专用模型 → 裂纹"改用裂纹自己的指标，颗粒和少样本模式的测量不变。
- **指标**：每条裂纹输出 `area_*`、`length_*`、`mean_width_*`、`aspect_ratio`（长度÷平均宽度，无量纲）。**长度**＝骨架（中轴线，`skimage.morphology.skeletonize`）长度，沿裂纹走向、含分支；**平均宽度**＝面积÷长度。列名同样带单位后缀（`length_px`/`length_um`，`mean_width_px`/`mean_width_um`），标定逻辑完全复用 `core/scale.py`。界面显示数量/平均长度/长度范围/平均宽度和两张分布图；Word 报告对应换成长度、平均宽度的统计与直方图。
- **骨架长度的数值方法**：数骨架像素的相邻步数。朴素权重（正交步1、对角步√2）在斜线上平均偏长5%、最大约10%；改用 Proffitt–Rosen 链码权重（正交0.948、对角1.340），在合成直线（26个角度×4种宽度）上平均偏差约0、最坏约6%。对角步只在2×2块内没有正交通路时才计，避免 L 形拐角被重复计费。骨架只有1个像素的紧凑小块长度按1 px 兜底，不丢行，保证行数和检测实例数一致。
- **合并过的裂纹**：裂纹专用模型会把同一条裂纹的几段合并成一个实例（见下），这些段彼此不相邻。`merge_disjoint=True` 时整个mask当作一个区域，长度是各段骨架长度之和，**段间空隙不计入**（实测两段各约94 px的分开笔画：不合并得到2行各93.9，合并得到1行187.7）。
- **验证**：合成直线长度201.9 px（真值约199.8），标定0.25 µm/px后长度、宽度均恰为像素值的0.25倍；真实 DenseCrack `image_001.png` 检出5条裂纹，长度49~559 px、平均宽度5.7~10.7 px；真实浏览器里上传该图，标定后显示的数值与脚本直接计算逐项一致，Word 报告可生成，颗粒模式同图仍给出原有指标。
- **已知局限**：①骨架对mask边缘毛刺敏感（每处毛刺变成一个短分支），形状很不规则时长度偏大；②宽度是整条裂纹的平均值，不是逐点宽度；③**没有拿人工标注的长度/宽度对照过**——DenseCrack 没有这类标注，只验证了算法本身和单位换算，没有验证和真实裂纹尺寸的吻合度；④裂纹的"数量"取决于合并半径和检测质量（见下），不应当作精确的裂纹条数。

### 可靠性校验（`core/reliability.py`）—— 弥补相似度分数不可信的问题

- **动机**：曾出现相似度分数 0.999~1.000（比任何真实成功案例都高）、但预测完全匹配到背景噪声的失败案例（NIST 月球颗粒 SEM 图）——证明**原始相似度分数不能作为"这次检测靠不靠谱"的依据**。
- **方案**：用"预测面积 / 参考面积"的比值做校验，超过 3 倍标记为不可靠。基于 5 个真实成功/失败案例回测校准，已接入 `FewShotDetector`、Streamlit UI（弹出警告）、`validate_few_shot.py`。
- **已知局限**：只能拦截"预测面积远超参考"（通常对应匹配到背景/无关区域），**拦不住"预测面积过小"**（欠分割，如单点在分叉处提前终止的裂纹案例）——这类问题要靠多参考点采样缓解，不是靠校验发现，产品设计上两者需要配合使用，不能只依赖校验模块。

### M5：网页端手动修正 mask（`core/mask_editor.py` + `app.py`）

- **动机**：不管零样本/少样本/穷举检测做得多好，总会有漏检或误检——尤其是穷举检测目前召回率只有约25%，需要一个兜底手段让用户自己补上。
- **交互设计**：编辑粒度是"整体区域"而不是"单个实例"——用户在画布上涂抹要新增或擦除的区域（"增加"/"擦除"两种画笔模式），不需要关心这一笔画跟原来哪个检测实例有关系。应用后，编辑结果重新走一遍连通域标记（`skimage.measure.label`），自动拆回一个个独立实例，直接对接现有的测量流程——用户完全不需要理解"mask"和"实例"的区别，只需要"觉得这里该有一个目标就画上，不该有就擦掉"。
- **实现**：`core/mask_editor.py` 三个纯函数（不依赖 Streamlit，可独立单元测试）——`masks_to_combined`（多实例合并成一个整体mask）、`canvas_layer_to_mask`（画布返回的RGBA笔画转成原图分辨率的布尔mask，用透明度通道判断哪里被画过）、`combined_to_instance_masks`（整体mask按连通域拆回多实例）。`app.py` 的 `mask_correction_ui` 负责画布组件（`streamlit-drawable-canvas`）的状态管理：每应用一笔就重建一次画布（靠改变 `key` 强制刷新，否则旧笔画会在画布里累积、重复叠加），编辑状态存在 `st.session_state` 里跨轮次保留。
- **关键验证**：`streamlit-drawable-canvas` 的 `image_data`（画布导出的RGBA数组）的透明度通道**只反映画的笔画，不包含背景图**——这是这个功能能不能做的前提，之前只是猜测符合预期，这次专门起了一个独立测试页面（300×300噪声图 + 画一小段线）用真实浏览器交互验证：非零透明度像素数（1494）和笔画本身的像素面积吻合，不是画布全部像素数（90000），确认背景图不会污染判断。
- **测试方式**：① `core/mask_editor.py` 三个函数各自单元测试（合成小数组，覆盖正常/空输入两种情况）；② `AppTest` 驱动真实检测流程（文字提示+上传真实SEM图片触发零样本检测），确认"手动修正"勾选框在有检测结果后正确出现、勾选后画笔模式单选框和"应用这一笔"按钮都能正常交互且不抛异常；③ 应用按钮点击后触发的 `st.rerun()` 撞到了 `AppTest` 测试框架对自定义前端组件的已知限制（无头环境模拟不了画布的真实前端交互，测试会卡住超时）——这是测试工具的边界，不是代码缺陷；实际浏览器里的真实笔画交互未做自动化端到端测试（文件上传本身在当前浏览器自动化工具里也无法模拟），需要用户在真实浏览器里手动验证一遍。
- **已知局限**：编辑粒度停在"一整块区域"，做不到"精修单个实例的边界"这类更精细的操作——如果用户反馈需要，是明确的后续扩展方向。（"合并两个实例"已在下方"实例操作"小节实现；"增加"笔画不再要求精细描边，见下方"框选重新检测"小节，不再是局限。）

#### M5 扩展：实例级"删除 / 合并"（`apply_pinned_groups`）

- **动机**：整体涂抹/擦除只能靠手工描边，删一个不规则形状的误检实例要沿边界精确擦干净很麻烦；合并两个视觉上分开（不相邻）但概念上是同一目标的碎片（比如被切成两段的裂纹）用画笔更是做不到——描边连接两段会把连接处也算进面积/周长，污染测量结果。
- **交互设计**：检测/编辑出当前的实例列表后，新增一个多选框按实例编号+面积(px)勾选，配两个按钮——"删除选中实例"（≥1个可点）直接从整体mask里抠掉选中实例的精确像素，不需要手工描边；"合并选中实例"（≥2个才能点）把选中实例标记为"绑定"，此后无论是否相邻都作为同一个实例参与测量。
- **实现**：`core/mask_editor.py` 新增 `apply_pinned_groups(combined, pinned_groups)`——`pinned_groups` 是历次"合并"操作产生的像素并集列表，处理时按顺序从整体mask里"认领"像素（后面的组会排除已被前面的组认领的像素，同一像素不会在两行输出里重复计数），认领剩下的部分才走原来的连通域拆分（`combined_to_instance_masks`）。返回 `(masks, n_pinned)`，`n_pinned` 是排在前面的"绑定组"行数。**绑定组不受 `MIN_INSTANCE_AREA_PX` 噪点面积下限限制**——用户主动选的，不该被自动过滤掉。
- **跟测量模块的接口**：`compute_particle_properties` 新增 `merge_disjoint` 参数——不传（默认）时用 `skimage.measure.label` 按连通域自动拆分（原有行为不变，因为正常检测结果每一行本来就是单个连通域，这个参数是不是加对已有路径完全没影响）；传 `True` 时把整个mask当成一个区域测量，不再重新按连通性拆分，用于"合并"产生的、像素本来就不相邻的那几行——否则 `compute_particle_properties` 自己内部的 `label()` 调用会把手动合并的结果又悄悄拆散，白合并了。`app.py` 里 `mask_correction_ui` 返回的 `n_pinned` 一路传到 `run_measurement_ui`，前 `n_pinned` 行传 `merge_disjoint=True`，其余照常。
- **验证**：① 纯函数级单测（合成3个不相邻色块）——不合并时等价于原来的连通域拆分；合并2个不相邻色块后正确产出1个绑定实例+1个普通实例，像素并集精确匹配；对比"不传 `merge_disjoint`"（验证确实会被错误拆回2个，证明这个参数是必要的、不是摆设）和"传 `merge_disjoint=True`"（正确测成1个）；从整体mask里删掉一个实例的像素后绑定组正确跟着消失；两个有重叠的绑定组不会重复计数同一像素。② `AppTest` 驱动真实零样本检测（文字提示"particle"+真实SEM图片，353个候选实例，零样本模式的已知噪点表现）——勾选"手动修正"后多选框正确列出全部353个实例，选中1个点"删除选中实例"后正确降到352个；"合并选中实例"按钮在选中不足2个时正确禁用，选中2个后启用，点击后正确合并成352个（353-1），下游的测量结果表格仍能正常渲染、无异常。

#### M5 扩展：单会话内把修正结果叠加为新参考图（`add_correction_as_reference`，仅少样本模式）

- **动机**：少样本模式的匹配质量取决于参考图集，一批目标图片里如果检测器在某张图上漏检/找错了，用户手动修正之后，这个修正本身就是一条"确认正确"的样本——与其让用户在后面每一张图上重复犯同一次错、每次都手动修正，不如把这次修正直接喂回参考图集，让同一次会话里*之后*渲染的目标图片自动受益。
- **范围收窄**（想清楚了再做，没有做成"自动学习"）：只做少样本模式，且只把用户主动确认的"新增/合并"实例当正参考喂回去，不处理"擦除"（负反馈方向复杂度和误伤风险都更高，参考此前"评估mask合并/连接方案"时的教训——后处理方法解决不了"分类器根本不认识"的问题）；零样本模式没有参考图概念，这条路完全不适用。而且是用户点按钮才生效，不是检测完自动做——修正质量对新图片不一定能泛化（比如这次修正是这张图特有的光照/聚焦巧合），静默自动叠加有可能把偏差也一起传播下去，做成显式操作用户才能判断要不要用。
- **实现**：`mask_correction_ui` 的"实例操作"区新增第三个按钮"加入参考图集"（仅在调用方传入 `on_add_reference` 回调时出现，零样本调用点不传，所以那边看不到这个按钮），要求刚好选中1个实例才能点。点击后调用 `add_correction_as_reference()`——对 `FewShotDetector` 调用一次 `set_reference()`（复用已验证过的"多参考图跑均值"机制，不是新写的匹配逻辑），并把一个新增的会话级计数器 `few_shot_ref_generation` 加一。
- **缓存失效设计**：批量上传的目标图片是在同一次脚本执行里用一个循环全部渲染的，每张图各自的检测结果缓存在 `cached_detect()`（`st.session_state`）。加一次参考图后，凡是缓存里记录的生成号对不上当前值的目标图都要失效——但**失效不等于立刻重新计算**（见下方"真实用户测试发现的问题"，第一版是立刻重算，实测会卡）；`add_correction_as_reference()` 只推高生成号，不主动摸其它图片的缓存，具体怎么处理失效是 `cached_detect()` 自己的逻辑（见下）。**触发这次操作的图片自己不能被这次失效误伤**——不然它自己的检测结果会被重新计算成一个新对象，`mask_correction_ui` 会把这当成"检测结果变了"从而清空用户刚做的修正，等于团灭自己刚确认的东西。解决方法：`add_correction_as_reference()` 在推高生成号的同时，把*当前图片自己*的缓存签名直接原地改写成新生成号（不改检测结果本身），让它在下一次重跑里继续命中缓存，不被重新计算。
- **顺手修的一个潜在小bug**：`cached_detect` 原来的签名只用 `id(detector)` 判断少样本检测器是否变化——由于 `detector` 是存在 `session_state` 里、原地修改的同一个对象，`id()` 在它的整个生命周期里从来不会变化（只有"清空全部参考图重新开始"整个换新对象才会变），这意味着此前如果用户在**看过一些目标图检测结果之后**又跑去第一步多确认了一张参考图，那些已经渲染过的目标图缓存根本不会失效——用的还是旧参考图集的检测结果。这个问题一直存在，只是没被注意到；这次引入生成号这个概念顺带修好了。
- **验证**：真实少样本流程走不到 `AppTest` 里（第一步"点击参考图目标结构"用的 `streamlit_image_coordinates` 是自定义前端组件，跟 M5 画布一样没法在无头环境里模拟真实点击），所以测试脚本绕过这一步——直接从 `session_state` 里取出真实的 `FewShotDetector` 对象，代码调用一次 `set_reference()`（跟真实点击最终触发的是同一个方法，只是跳过了产生这次调用的前端交互），后续检测、勾选修正、点"加入参考图集"全部走真实 `app.py` 代码路径。

#### M5 扩展："增加"笔画改成框选重新检测，而不是直接用手绘像素（`SamSegmenter.decode_box`）

- **动机**：用户反馈"增加"模式手动描边太精细、画出来的形状跟真实颗粒边界对不上；同时另一份真实报告（`1908252.tif`）暴露的"检测多出来的"问题，追查发现是SAM对一个点提示解码出了横跨两颗粘连颗粒的mask（花生形，两个鼓包）——这类情况原来的修复方式（手动擦掉再精细描边补两个）对用户来说太麻烦，画的形状本来就不准，等于用不精确的手绘去修一个不精确的检测。
- **方案**：复用穷举检测里 `decode_point()` 已经验证过的思路，"增加"模式不再直接把画布上涂的像素当成最终mask——改成取这一笔涂抹范围的**外接矩形**，当作 SAM 的 box 提示，新增 `SamSegmenter.decode_box()`（用法和 `decode_point()` 一样：`multimask_output=True` 选 SAM 自己预测IoU最高的候选），用 SAM 在这个大致范围内自己去找真实边界。用户只需要大致框住/涂抹目标，不需要精细描边；框选还有个额外好处——针对"一个检测其实是两颗粘连颗粒"这种情况，在下方"实例操作"里删掉这个错误检测后，分两笔大致框住两颗颗粒（两笔之间留出空隙），SAM 会分别在各自的框里独立找边界，不会像单点提示那样容易越界抓到隔壁颗粒。"擦除"模式不变，仍然是精确按涂抹像素直接减掉——去掉一块区域没有"真实边界"要找，手绘本来就是精确的操作。
- **实现**：`core/mask_editor.py` 新增纯函数 `stroke_bounding_box(stroke_mask)`，笔画为空时返回 `None`（用户点了应用但没画东西，直接跳过，等价于原来的空笔画无操作）。`mask_correction_ui` 现在需要传入 `sam_segmenter` 参数——"增加"模式应用时先 `sam_segmenter.set_image(image)`（复用已有的按 `id()` 跳过重复编码的机制，画同一张图的多笔不会重复付编码的钱，切到另一张图纠正过才会真的重新编码）再 `decode_box()`；如果 SAM 对某个退化的框（比如一个点）解不出有效mask，兜底直接退回用户涂的原始像素，不会让这一笔白画。
- **验证**：用真实 EMPS 数据里两颗真正粘连的颗粒（外接框有17px重叠）验证——构造一个刻意粗糙、边界明显超出真实颗粒轮廓的"手绘框"，直接拿这个粗糙框当mask的话跟真实颗粒的 IoU 只有 0.669；同一个框走 `decode_box()` 之后 IoU 提升到 **0.973**，且跟旁边那颗真实颗粒的重叠从粗糙框自带的7.4%降到 **0%**——证实了这个改动确实能把"随手一框"变成"精确边界"，而不只是理论上应该有效。
- **已知局限**：这个改动只覆盖"增加"模式；"精修单个已有实例的边界"（不新增，只调整现有实例的轮廓）仍然做不到，如果用户反馈需要，是下一步方向。

#### 真实用户测试发现的问题：加一次参考图，其它图片的检测"迟迟出不来"，已修复

- **现象**：用户实测反馈"点了手动修正后，第二张图的检测迟迟没有完成"，追问后确认是刚点过"加入参考图集"（或在第一步又多确认了一张参考图）——不是卡死，就是一直转圈出不来。
- **根因**：第一版实现是"生成号一变，凡是签名对不上的目标图立刻重新检测"，而且是在触发操作的**同一次** `st.rerun()` 里完成的——Streamlit 全脚本重跑是同步阻塞的，这意味着点一下"加入参考图集"，页面要等**这批里所有其它目标图片各自重新跑一遍完整检测**（每张至少一次SAM编码~9.5秒，穷举模式还要再加上最多150次解码）才会有任何响应。图片一多、或者用什么穷举模式，这个同步等待能拖到几分钟，体验上就是"点一下卡半天"。这是我在上一版实现时低估了这个代价、事后才发现的设计问题，不是这次新暴露的偶发bug。
- **修复**：把"缓存失效"和"要不要立刻重算"拆成两件事。`cached_detect()` 新增 `stale_token` 参数（就是 `few_shot_ref_generation`）：只有 `base_signature`（预处理开关、检测器身份等，用户直接改的、只影响这一张图的设置）变化才会像以前一样立刻同步重算；`stale_token` 单独变化时**不重算**，改成返回 `is_stale=True` 和一个 `refresh` 回调，调用方（少样本两处检测入口）据此显示一条"参考图集自上次检测后已更新，下面暂时仍是旧结果"提示 + 一个"用最新参考图集重新检测"按钮，只有用户主动点这个按钮才真正付这次重新检测的开销。这样加一次参考图本身几乎是瞬间的（只有 `set_reference()` 编码一次新参考图的开销），其它图片该多慢还是多慢，但只有用户真正想看新结果的那一张才会等。
- **验证**：`AppTest` 复现真实场景（原理同上，绕过参考图点击这一步，其它全走真实代码路径）——两张目标图检测完后，在图A上点"加入参考图集"：图A自己的缓存签名立刻更新（不重算，修正保留），图B的缓存签名**保持不变**（没有被强制重算，这正是这次要修的问题），并且正确出现"重新检测"按钮；点这个按钮后图B才真正重新检测，签名才更新到新生成号，按钮随之消失。

#### 真实用户测试发现的严重问题：涂抹后页面卡死，已修复

上线第一次真实测试就发现"涂抹后页面几乎完全卡住，很久没有反应"——排查后是**三个叠加的架构问题**，不是画布本身的锅：

1. **检测结果完全没缓存**：Streamlit 的机制是任何控件交互都会把整个脚本从头重跑一遍。画布上的每一笔（鼠标松开触发一次rerun）都会把 `detector.detect_all()` 或 `detector.detect()`+`sam.segment()`（穷举模式下要9~20多秒）从头重新算一遍，算完才能把画布重新显示出来。**修复**：新增 `cached_detect()`，用 `st.session_state` 按"文件+预处理开关+参考图集合"做签名缓存，签名不变就直接复用上次的检测结果。
2. **预处理也完全没缓存**：`preprocess()` 里的 `cv2.fastNlMeansDenoisingColored`（去噪）算法出了名地慢，同样因为没缓存，每次画布交互都要重新跑一遍。**修复**：新增 `cached_preprocess()`，用 `@st.cache_data` 按图片字节内容+预处理开关缓存，这是纯函数场景，比手写的 session_state 缓存更合适。
3. **`combined_to_instance_masks` 在噪点多的情况下有真实的性能坑**：排查用户报告时用同样的图（零样本模式检测致密颗粒图像，已知的失效场景）复现，发现检测结果被连通域标记拆成了 **734 个碎片**（零样本在这类图像上的失败表现就是满屏噪点，不是一个干净的大团块）。原实现对每个连通域都单独生成一张和原图等大的布尔数组，`overlay_masks` 又要再遍历一次全部上色——这是 O(实例数×图像尺寸) 的真实性能问题，不是测试工具的假象，734个实例在这台机器上单这一步就要9秒以上。**修复**：给 `combined_to_instance_masks` 加上和 `measurement.py` 一致的噪点面积下限（`MIN_INSTANCE_AREA_PX=25`），微小碎片在拆分实例这一步就被过滤掉，不进入后续渲染和测量流程。
- **修复效果**：3个缓存/过滤修复叠加后，同一个（刻意选来复现问题的、零样本模式的、已知失效的）测试用例耗时从约30秒降到约15秒——**有实质改善但未完全消除**，因为零样本模式在这张图上产生的噪点碎片过滤后仍有353个，这本身反映的是零样本模式的已知局限（"完全失效...没有实例级定位能力"），不是M5编辑器该去兜底的场景。**真正该验证的是少样本模式**（文档记录的可靠主力方案，掩膜通常干净、实例数少）下的实际体验，目前还没有真实用户在少样本模式下测试过修正功能的流畅度。
- **调试方法记录**：这次排查全程靠往代码里插 `print` 时间戳、跑 `AppTest` 触发真实检测流程来定位，不是靠猜——先怀疑"AppTest本身开销大"，用一个"页面上没有任何检测结果、只切换侧边栏勾选框"的对照组证伪（0.0秒，排除了"AppTest天生慢"这个假设），再用细粒度埋点一行行定位到具体是哪一步慢，最后精确定位到 `combined_to_instance_masks` 里的 734 实例。

### 性能优化：`SamSegmenter` 消除重复编码

- **动机**：思考"怎么让模型更轻量"时排查代码发现的真实浪费，不是猜测——`SamSegmenter.segment()` 每次调用都无条件重新跑一遍 SAM 图像编码器。单目标少样本模式的调用链 `detector.detect(processed)`（内部已编码一次算相似度热力图）→ `sam.segment(processed, prompt)`（又编码一次）对**同一张图编码了两遍**。`detect_all()`（穷举模式）设计时就注意到了这一点、全程只编码一次（见 `decode_point()`），但更常用的单目标路径一直没有顺手修。
- **修复**：`SamSegmenter.set_image()` 记录上次编码过的图像对象（`id()` 比较，不比较像素内容——比较大数组内容本身也有开销，抵消了想省的这次编码），同一个数组对象重复调用直接跳过编码。
- **验证**：① 用计数器包裹真实的 `predictor.set_image` 调用，确认"同一图像对象调用两次只编码一次""不同图像对象各自正常编码"两种情况都符合预期；② 实测单目标少样本检测总耗时从约26.7秒降到约17.5秒（降低约35%），`segment()` 单独耗时从约9.5秒（含重复编码）降到0.26秒（只跑解码器）。
- **其它轻量化方向（已想过，未实施）**：SAM backbone 换成 MobileSAM（蒸馏过的 TinyViT 编码器，宣称CPU快5倍左右，`segment_anything` 的 predictor 接口兼容，是目前最值得做的模型级优化）；SAM 导出 ONNX 用 ONNXRuntime 跑（能跟 MobileSAM 叠加，但工程量更大）；`torch.compile()`（低成本可以试，但CPU上收益不确定，容易在自定义算子上翻车）。Grounding-DINO 已经在用官方最小的 SwinT（Tiny）变体，颗粒分类器本身就很小，都没有进一步瘦身空间。

### 设备选择：新增 `core/device.py`，MPS 在这台机器上实测更慢

- **背景**：用户提到近期要换 Apple Silicon（M5）机器，问能不能借此减少版本兼容问题。当前 `torch<=2.2.2` 等一系列版本锁死是 **Intel macOS 专属限制**（PyTorch官方不再为x86_64 macOS发布2.2.2之后的wheel），Apple Silicon 上这条链路的版本锁应该能大幅放松。
- **顺手发现的问题**：`SamSegmenter`/`ZeroShotDetector` 原来的设备选择逻辑只检查 `torch.cuda.is_available()`，没有检查 `torch.backends.mps.is_available()`（Mac的GPU加速后端）——即使换了新机器，代码原样不动的话也完全用不上新硬件的GPU，会一直在CPU上跑。已抽出共享的 `core/device.py::resolve_device()`（cuda > mps > cpu 优先级），两处调用点都改用它。
- **意外发现，而且是关键的一步**：**MPS 不是 Apple Silicon 专属**——只要有 Metal 兼容的 GPU 就能用，这台 Intel Mac 自己就有（`Intel HD Graphics 630` 核显 + `Radeon Pro 560` 独显），`torch.backends.mps.is_available()` 在这台机器上返回 `True`。加上 `resolve_device()` 后**这台机器现在就会开始用 MPS**，不是等新机器才生效——所以必须在这台机器上先实测一遍，不能想当然。实测：**MPS 编码一张图要 21.74 秒，比 CPU 的 9.5 秒还慢近一倍**（AMD GPU 在 PyTorch 的 MPS 后端上不如苹果自研芯片成熟，这块 Radeon Pro 560 本身也不算新）。
- **处理方式**：`config.py` 的 `DEVICE` 显式改成 `"cpu"`（不再是 `"cuda"`），附注释说明原因和测出的数字。`resolve_device()` 的 cuda>mps>cpu 逻辑本身没问题，保留着，等真正换到 Apple Silicon 后把 `DEVICE` 改回 `"cuda"`（会自动解析成 `"mps"`）**并重新实测**——苹果自研GPU的MPS成熟度通常好很多，但"通常"不是"一定"，这次的教训就是不能跳过实测直接假设新硬件更快。

#### 后续更新：真换到 Apple Silicon（M5 Pro）后重新实测，`DEVICE` 改回 `"cuda"`

- 新机器到手，按迁移清单重建了 `.venv`（原生 arm64 Python 3.11，装 Python 前发现从 Intel Mac 迁移过来的 `/usr/local/Homebrew` 是 x86_64 版本、这台机器连 Rosetta 都没装，完全跑不动，先清掉换成 `/opt/homebrew` 原生版）、依赖照 `requirements.txt` 原样装（**这一步没有顺带升级 torch 版本**——一次只变一个变量，先确认迁移本身没问题，升级版本是刻意放到后面的独立步骤）。
- 按上面记的教训，没有直接假设"苹果自研芯片就一定更快"，重新跑了一遍同样的基准测试：SAM 编码同一张图，**MPS 平均 0.33秒/张，CPU 平均 1.30秒/张**（各自热身后取3次平均）——这次 MPS 确实快得多（约4倍），且这台机器本身的 CPU 单核性能也比旧 Intel Mac 快不少（1.30秒 vs 旧机器的9.5秒）。跟旧 Intel Mac 那次结论相反，印证了当时的判断：差的是那块老 AMD 独显在 MPS 后端上不成熟，不是 MPS 这条技术路线本身不行。
- `config.py` 的 `DEVICE` 改回 `"cuda"`（解析成 `"mps"`），注释更新为这次实测的数字。真实 `AppTest` 跑通零样本检测端到端验证：23.9秒（旧 Intel Mac CPU 上同样流程约40-60秒）。

#### 后续更新：torch 从 2.2.2 升到 2.14.0（单独一步，不跟迁移绑一起做）

- 环境迁移稳定之后，单独把 `torch`/`torchvision` 从 Intel Mac 时代锁死的 2.2.2/0.17.2 升到当前最新的 2.14.0/0.29.0——没有先猜一个"看起来安全"的中间版本，直接试最新版，pip 的依赖解析器很快就会告诉你不兼容（便宜、快的信号）；`torchvision` 的 pip 元数据会强制要求匹配 `torch` 的具体版本（例如这次要求精确的 `torch==2.14.0`），以后再升级要两个一起升，不能只动一个。
- 结果比预想的干净：**`numpy<2` 这个锁没有被 torch 2.14 强制打破**（之前以为是 torch 2.2.2 逼出来的限制，这次验证发现 torch 2.14 其实不强制要求 numpy>=2，这个锁现在真正的来源是 `opencv-python-headless==4.10.0.84` 自己的wheel可用性，注释已更新）；`transformers==4.44.2` 原样能用，不需要跟着升级。
- **验证不只是能 import**：用真实 BAM_TiO2/EMPS 数据重新跑了一遍之前验证过的两个SAM相关修复（环形mask补洞、`decode_box`框选重新检测）——`decode_point()` 在 torch 2.14 + MPS 上跑出来的mask面积跟升级前 torch 2.2.2 + CPU 的结果**逐像素完全一致**；另外跑了一遍真实 `AppTest`（零样本检测 → 启用M5 → 删除实例）端到端确认没有回归。只有来自 Grounding-DINO 自身代码用了几个新版 torch 标记为过时（deprecated）但还没删除的API的警告（`torch.cuda.amp.autocast`、`checkpoint` 的 `use_reentrant` 参数等），不影响功能，是上游代码的技术债，不是这个项目要修的。

### 训练专门的实例分割模型（Mask R-CNN），替代 SAM+分类头穷举检测的召回率天花板

该方案最初在内部研究计划中形成；这里保留最终采用的技术路线与实验依据。

- **数据**：只用 `EMPS`（366 张 train.txt，真正的逐颗粒实例级标注）训练，`BAM_TiO2` 留作完全没参与训练的域外验证——理由和上面"穷举检测"小节的分析一致：`BAM_TiO2` 只有二值 mask，连通域分出来的"实例"会把粘连颗粒并成一个，直接喂给模型错误的监督信号，等于重蹈现有方法的失效模式。
- **模型**：`torchvision.models.detection.maskrcnn_resnet50_fpn_v2`（COCO 预训练），替换 box/mask 两个头做单类别（"particle"），冻结 backbone（ResNet-50，占比51.2%参数），只训 FPN+RPN+ROI heads（22.4M/48.8%参数）。脚本：`scripts/train_instance_segmenter.py`。
- **训练**：冒烟测试（16图/3epoch）确认流程无误并实测单epoch耗时后，在 Apple M5 Pro（MPS）上对全部366张训练图跑了20个epoch，约56分钟。Loss从0.6622平稳降到0.2132，全程没有震荡或过拟合迹象。
- **评估**（`scripts/evaluate_detector.py`，与之前"评估口径改成严格一对一匹配"小节同一套方法：IoU≥0.5、`scipy.optimize.linear_sum_assignment` 一对一匹配）：

  | | 数据集 | 是否同域 | 召回率 | 精确率 | 命中平均IoU |
  |---|---|---|---|---|---|
  | **新模型（instance_seg）** | EMPS test（99图，2579颗真值） | 同域 | **85.8%** | **91.6%** | 0.913 |
  | **新模型（instance_seg）** | BAM_TiO2 test（8图，1658颗真值） | 域外 | 32.0% | 80.3% | 0.801 |
  | 现有穷举检测（few_shot baseline） | BAM_TiO2 test（同一批8图） | — | 22.1% | 66.3% | 0.804 |

  同域（EMPS）上召回率从旧方法的25-33%天花板直接跳到85.8%，精确率也同时提升，这就是训练专门模型要解决的问题。**更值得注意的是域外结果**：新模型完全没见过 `BAM_TiO2` 一张图，在同一批8张留出图上，召回率（32.0%）和精确率（80.3%）却都**超过**了专门在 SEM 颗粒图像上调过参数的现有穷举检测基线（22.1%/66.3%）——说明"真正学会分割颗粒实例"这件事本身有跨材料/跨成像模式的泛化能力，比"SAM冻结特征+零训练分类头"这条路径更扎实。
- **`box_detections_per_img` 上限截断了域外召回率，调大后验证有效**：检查逐图日志发现，`BAM_TiO2` 8张留出图里有**5张**（`1908314`/`1908318`/`1908320`/`1908324`/`1908326`，真值都在199~410颗）的预测数精确卡在100——`maskrcnn_resnet50_fpn_v2` 默认的 `roi_heads.detections_per_img=100` 是打分排序后"只留前100个"的最终截断，是推理时的后处理参数，不是训练出来的权重，出现这么高的撞限比例（5/8）而不是个别情况，值得直接验证而不是当成边缘案例忽略。EMPS同域99张测试图只有2张（约2%）撞到这个限制——`BAM_TiO2`颗粒本身又小又密（单图动辄两三百颗）是主因。改成500后重新评估域外表现：召回率 32.0%→**40.7%**（+8.7个百分点），精确率基本没掉（80.3%→78.4%），平均IoU几乎不变（0.801→0.795）——新增的检测大部分是真实命中，不是靠放宽阈值硬凑数字；改后8张图里没有一张再撞到500这个新上限（最多用到179），说明继续调大边际收益应该很小了。这个参数已加进 `scripts/evaluate_detector.py` 的 `--detections-per-img` 命令行参数，方便复现。
- **另一处已知偏差**：`BAM_TiO2` 的评估GT本身来自二值mask连通域，跟训练时排除它的理由一样——粘连颗粒会被GT合并成一个实例，域外召回率数字有轻微的正向偏差（同一个合并区域，模型只要对上一个检测就算全对）。
- **权重**：`models/instance_segmenter.pth`（gitignore，183MB）。

#### 接入 app.py：新增"专用模型"识别模式

- `core/detectors/instance_seg.py::InstanceSegmenter` 把训练好的 Mask R-CNN 包成跟 `SamSegmenter.segment()` 一样的 `(N,H,W)` bool mask 堆输出契约，`app.py` 现有的 M5 修正/测量/报告导出流程不用改一行就能复用。加载时用 `weights=None, weights_backbone=None` 构建骨架（不触发任何预训练权重下载），完全靠 `load_state_dict()` 从训练好的 checkpoint 恢复全部参数——这个app要求全程离线运行（见 `app.py` 顶部注释），加载步骤不能依赖网络。
- 这个模式不需要参考图也不需要文字提示，上传图片就直接输出所有实例；UI 文案如实标注了同域/域外的召回率精确率数字（不包装成"已解决"），并提示此模式用的是未预处理的原始图像（跟训练时一致，边栏预处理开关在这个模式下不生效）。`detections_per_img` 默认设为300（介于验证过的100/500之间，实测8张BAM_TiO2留出图最多只用到179）。
- **验证方式**：跟M5画布/参考图点击组件一样，文件上传本身是原生系统对话框，工具链没法自动化模拟真实点击上传，没有做完整的端到端浏览器验证。已验证的部分：① 真实 `AppTest` 确认模式切换、模型加载、UI文案渲染都不抛异常；② 真实浏览器里确认三个模式的单选框、新模式的说明文字、文件上传控件渲染正常；③ **绕过Streamlit直接调用**（`InstanceSegmenter.predict()` → `compute_particle_properties()` → `masks_to_combined()`/`combined_to_instance_masks()`，用真实BAM_TiO2图像）确认底层数据流真的能跑通、shape/dtype全程匹配，不是只测了UI皮肤。
- **已知的架构级限制，先如实记录**：M5手动修正的当前实现是"所有实例先合并成一个总mask，之后统一按连通域重新拆分"（见上方"M5：网页端手动修正mask"小节），这对SAM单点/单框检测的结果没问题，但对这个新模型会有反效果——Mask R-CNN训练的整个意义就是正确拆开互相接触/粘连的颗粒，可一旦用户在这个模式下打开M5手动修正，哪怕什么都不涂改，几个原本被模型正确分开的、边界相邻的实例也会被这一步连通域重新拆分合并回一个。真实验证过（同一张BAM_TiO2图）：模型直接输出51个实例，走一遍`masks_to_combined`+`combined_to_instance_masks`后只剩9个。这不是这次新引入的bug——少样本穷举检测走同一段M5代码，有一样的限制——但对这个模型的影响更大，因为"拆开粘连颗粒"正是它相对旧方法的核心优势。暂时的应对：UI文案没有隐瞒这一点的必要性判断（用户可以选择不开启M5，直接用模型的原始输出），真要修，需要让M5支持保留"预先分开但相邻"的实例，这是M5架构本身的后续工作，不是这次UI接入要解决的范围。
- **已修复（`keep_instances`）**：`mask_correction_ui(keep_instances=True)` 让每个检测实例在编辑过程中保持独立（`core/mask_editor.py::apply_pinned_groups` 新增 kept 阶段：先用户合并组，再检测实例，最后才是新增笔画的连通域拆分）。**同一张 BAM_TiO2 图：不开 `keep_instances` 51→9；开启后 51→47，前景像素 47098→47075**。少掉的4个不是被误合并，而是几乎被前面的重叠 mask 覆盖（模型输出里有 48 对互相重叠的 mask，这4个剩余面积分别只有 1/16/0/6 px，低于25 px 噪声下限）——本质是近似重复的预测。副作用：开启编辑后，重叠区域归先出现的那个实例，所以面积与未编辑时略有差别。颗粒专用模型和少样本穷举检测启用；普通少样本单目标不需要。
- **同时修掉的另一个 bug**：裂纹模式下「合并选中实例」按钮实际是空操作——原始实例的固定组排在用户新合并的组前面，先把像素占光，合并组分到的像素为空。现在用户合并组（最近一次的排最前）排在检测实例之前处理。有单元测试覆盖（含嵌套合并）。
- **暂不做的事**：`score_threshold`/`detections_per_img` 目前是代码里的固定默认值，没有做成UI上可调的滑杆——不确定用户是否需要这个粒度的手动调参，等有实际反馈再决定要不要加。

#### 裂纹专用模型：`专用模型 → 目标类型 → 裂纹`

- **为什么要有**：颗粒专用模型（上节）训练数据全是 EMPS 颗粒，从没见过裂纹；少样本的穷举检测同样不认识细长目标（见上方"裂纹场景的教训"）。比赛版不要求严格少样本，所以为"专用模型"模式加了第二个模型和"颗粒/裂纹"目标类型开关。
- **模型**：同样是 `maskrcnn_resnet50_fpn_v2`（COCO预训练、冻结backbone），单类别"crack"，**把 RPN 锚框长宽比加宽为 (0.1, 0.2, 0.5, 1.0, 2.0, 5.0, 10.0)**——默认的 (0.5, 1, 2) 是为 COCO 的团块状物体设计的，实测20张 DenseCrack 图里实例长宽比中位数3.35、54%大于3、26%大于5。脚本：`scripts/train_crack_segmenter.py`；包装类：`core/detectors/crack_seg.py::CrackSegmenter`，输出契约同样是 `(N,H,W)` bool mask堆，M5/测量/报告流程复用。权重 `models/crack_segmenter.pth`（gitignore）。
- **数据：只用 DenseCrack**（510张显微尺度密集微裂纹，训练410张、官方测试集100张）。真值是二值mask，用连通域当"实例"，对裂纹比对粘连颗粒可接受（一条真实裂纹通常是一条连通路径）。**CrackSeg9k 试过并排除**：它是宏观照片（路面、墙面等）、成像方式和本项目的显微域不同，掺进训练后 DenseCrack 上的指标反而下降（旧版混合训练权重保留在 `models/crack_segmenter_v1_mixed_domain.pth` 作对照）；它只用作域外评估。**MetalDAM 的"Defect"类也评估后放弃**：只有36个实例，大多是团块状而不是细长裂纹（长宽比中位数1.48）。DenseCrack 里有41/510张图像与mask尺寸不一致，训练和评估都用最近邻把mask缩放到图像尺寸。
- **精确率问题和合并后处理**：初版在 DenseCrack 测试集（严格一对一匹配、IoU≥0.5，`scripts/evaluate_crack_detector.py`）召回率75.4%，但**精确率只有42.3%**。排查发现不是误检，而是**一条连续的裂纹被预测成沿长度方向的几段局部检测**（67%的真值被≥2个预测明显覆盖，且这些预测彼此IoU很低——是首尾相接的片段，不是重复框），严格一对一只给一段记分，其余全算误检；这些"误检"里95.4%确实落在真实裂纹像素上。普通按IoU的NMS抓不住（片段互不重叠）。**修复**：膨胀后相接的mask用并查集合并成一个实例（`merge_nearby_masks`，合并结果取原mask的并集，膨胀只决定谁和谁一组）。**必须真值和预测两边都按同一半径合并**——只合并其中一边，指标反而变差，因为口径不一致。合并半径扫描：

  | 合并半径 | 召回率 | 精确率 | 命中平均IoU |
  |---|---|---|---|
  | 0（不合并） | 75.4% | 42.3% | 0.749 |
  | **10 px（采用）** | **74.8%** | **73.0%** | **0.741** |
  | 20 px | — | — | 0.721（不同裂纹开始被误并，IoU下降） |

  合并后精确率从42.3%升到73.0%，召回率基本不变。**要如实说明口径**：这个73.0%是"预测和真值都做了10 px合并"后的数字，真值本身来自二值mask的连通域而非逐实例标注，和颗粒模型的 EMPS 逐实例真值不是同一档可信度。
- **留出验证（`scripts/select_crack_merge_radius.py`）**：上面的 r=10 是在 DenseCrack 测试集上扫出来、又在同一批图上报告的，选择和报告共用同样100张图，精确率偏乐观。模型训练时用了全部410张训练图、没有验证集，所以把测试集随机拆成两半：**半径只在一半图上按 F1 选，再在另一半上报告**，20次随机拆分×双向共40组，汇总：召回率**72.2%**、精确率**71.4%**（同集选择的是74.8%/73.0%，高估约2个百分点；不合并是75.4%/42.3%）。40次选择里选到10 px 的22次、15 px 的10次、20 px 的6次、12 px 的2次，没有选到8 px 以下的；10~15 px 之间曲线很平（全量扫描 F1 都约0.73）。r=10 对100张图做 bootstrap 的95%区间：召回率68.3%~81.0%，精确率66.7%~79.2%——**100张图本身的抽样不确定性比"同集选半径"的偏差更大**。结论：合并带来的精确率提升（约+29个百分点）是真实的，具体数字宜按"约71%~73%"引用。仍未解决：真值是连通域近似而非逐实例标注。
- **域外**：宏观裂纹集 CrackSeg9k 上召回率3.1%、精确率6.1%（命中平均IoU 0.624）——基本不能用，UI 文案里已如实写出，并提示先用少量图像试跑核对。
- **合并实例和后续流程**：合并后的一个实例可能由互不相邻的几段构成，而 M5 的连通域重新拆分、`compute_particle_properties` 的连通域拆分都会把它们又拆开，白合并。所以裂纹模式下 `mask_correction_ui(preserve_groups=True)` 把所有检测实例都当作已固定的合并组，`run_measurement_ui` 对它们按 `merge_disjoint` 当整体测量（用真实浏览器验证：5个实例→表格5行→5个"（已合并）"固定组）。
- **已知局限**：①裂纹模型没有可靠性校验，只靠 Mask R-CNN 自己的置信度（阈值0.5）；②训练数据单一（DenseCrack），其它材料/成像方式预期明显退化；③合并半径10 px 是在 DenseCrack 上扫出来的，不同分辨率的图像未必最优，没做成界面可调。

### 融合路线评估（`scripts/evaluate_fusion.py`）—— "专用模型 + 参考图打分"的硬阈值过滤不划算

- **背景**：`app.py` 的少样本"穷举检测"里，比赛版加了一个候选来源选项"专用模型 + 参考图打分"：候选来自实例分割模型，再用 `FewShotDetector.score_masks()` 的参考图余弦相似度做硬阈值过滤（滑杆，默认0.78）。此前只量过相似度能不能分开同/异材料的掩膜（EMPS 同材料中位数0.886 vs 不同材料0.754，范围重叠），**整条流水线的召回率/精确率没有测过**。
- **方法**：严格一对一匹配（IoU≥0.5，匈牙利）。预处理与 app 默认一致（候选用原图，打分用去噪+均衡化后的图）。参考来源四类：①**self** 参考取自目标图自己的真值（最有利）；②**cross-same** 取自同数据集另一张图；③**cross-other** 取自另一种材料（EMPS↔BAM_TiO2，即用户选错材料）；④**mosaic** 把 EMPS 图和 BAM_TiO2 的512×512裁剪并排拼成30张合成混合图、只要其中一种材料（过滤本该有用的场景）。参考大小两种：n1＝一个中位数大小的颗粒（≈一次点击），n3＝小/中/大三个。阈值扫描 0~0.90，**没有在这些数字上调任何参数**。
- **结果（n1，阈值0.78，括号内为不过滤时）**：

  | 场景 | 召回率 | 精确率 | 相似度AUC |
  |---|---|---|---|
  | EMPS 99图，self | 63.4%（88.8%） | 94.0%（91.7%） | 0.654 |
  | EMPS，cross-same | 27.4% | 92.3% | 0.550 |
  | BAM_TiO2 8图，self | 14.3%（40.7%） | 82.0%（78.4%） | 0.545 |
  | BAM_TiO2，cross-same | 17.6% | 82.0% | 0.545 |
  | EMPS 参考 → BAM_TiO2 目标 | 8.9% | 83.5% | 0.530 |
  | BAM_TiO2 参考 → EMPS 目标 | 10.1% | 90.0% | 0.547 |
  | 混合图，只要 EMPS（30张） | 12.2%（69.4%） | 32.8%（22.1%） | 0.537 |
  | 混合图，只要 BAM_TiO2（30张） | 8.2%（47.4%） | 66.2%（60.1%） | 0.478 |

  n3 结论一致（例：EMPS self 召回率69.3%/精确率94.0%，cross-same 34.5%/93.0%，BAM_TiO2 self 16.3%/78.1%）。
- **结论**：①所有场景下硬阈值过滤都是净损失——召回率大降，精确率只涨0~3个百分点（专用模型的候选本来就很准，EMPS 上91.7%）。②相似度几乎分不开"命中真实颗粒的候选"和"其它候选"（AUC 0.48~0.66，接近随机）；在混合材料合成图上也分不开两种材料（只要 BAM_TiO2 时AUC 0.478，低于随机）。③阈值越高召回率越低，**没有哪个阈值在 F1 上优于不过滤**。所以这个选项只适合当对照演示，不应作为主流程；该选项本来就是非默认（候选来源单选框默认"分类器峰值"）。
- **口径提醒**：EMPS 的"另一张图"是随机挑的，可能与目标图同源；混合图是人工合成，不是真实混合样品；BAM_TiO2 只有8张测试图，真值是连通域近似；有6个太细的参考掩膜在 SAM 的64×64特征网格上消失而被跳过（不影响结果）。
- **复现**：`python -m scripts.evaluate_fusion --mosaic-pairs 30`（n1、n3 各约5分钟，Apple M5 Pro）；`--ref-sizes n1`/`n3` 单跑一种参考大小。

### 参考颗粒选取引导（`core/reliability.py::check_reference_selection`）

- **动机**：用户实测 `1908254.tif`（BAM_TiO2）导出的报告只识别出 58 颗，肉眼能数出至少 15-20 颗明显漏检，集中在颗粒粘连的团簇区域——这跟已知的穷举检测召回率天花板一致，但顺带确认了待办第1条（参考颗粒选取敏感）还没有任何产品层面的引导，纯靠用户自己判断。
- **先做了两版都失败的尝试**（如实记录，不是最终方案，别重复踩坑）：
  1. **形状特征（solidity）判断是否为粘连团簇**：实测 BAM_TiO2 真实标注——面积接近中位数（大概率单颗粒）的区域 solidity 均值/中位数 0.895/0.938，面积≥3倍中位数（大概率是团簇）的区域反而是 0.872/0.905，两组几乎完全重叠，不是可用的分界特征（跟穷举检测分类器那次"形状特征二级级联"诊断阶段发现的问题是同一个结论）。
  2. **Otsu阈值+连通域粗估每张图的颗粒密度**，用来判断"这张图是否稀疏"或"这个区域是否比本图典型颗粒大很多"：在全部40张可用 BAM_TiO2 图上跟真实标注核对，Otsu 会把粘连颗粒合并计数，不同图片的合并程度差异很大（欠计数倍率从1.4倍到6倍不等，没法用固定系数校正）——**42%的真实密集图（标注≥40颗）被误判成"稀疏"**，**62%的真实中位数大小颗粒被误判成"团簇过大"**。误报率高到会让用户不再信任这个提示，不能用。
- **最终方案（两个信号都不依赖临时估计，落地更可靠）**：
  1. **绝对面积过小警告**：复用穷举检测根因分析里已经验证过的结论（颗粒特征在 SAM 64×64 特征网格上占的格子数太少会跟背景混叠）——选中区域面积换算成网格格子数，低于2个格子就提示。不需要猜这张图"典型颗粒多大"，只用 SAM 自己的固定分辨率算。
  2. **跟本次会话已确认的参考图比对**：多参考图场景下，`FewShotDetector` 会把几张参考图的特征取平均当成同一类目标——如果新选的区域面积跟已确认的参考图平均面积差异超过2倍（无论偏大偏小），提示"确认这是同一类目标，不是不小心选到了粘连团簇或明显不同大小的颗粒"。用的是用户自己已经确认过的选择做基准，不是重新估计的、不可靠的密度信号。
  3. **如实说明覆盖范围**：SOURCES.md 记录的"选稀疏图+小颗粒（658px）"这个具体历史失败案例，按新方案的绝对面积阈值算不会被拦下来（658px 在常见图像尺寸下超过2格子的门槛）——这两个信号能拦住的是"特征网格分辨率不够"和"多参考图大小不一致"这两类结构性风险，不是"稀疏图更容易匹配到背景"这个更难可靠估计的问题，没有夸大覆盖面。
- **验证**：合成数据覆盖"过小"/"跟已有参考差异过大"/"两者同时触发"三种情况；额外在20张真实 BAM_TiO2 图上取每张的中位数面积真实颗粒验证零误报（新方案不依赖任何临时密度估计，之前 62% 的误报来源已经不存在）。UI 交互本身（点击参考图那一步）用的自定义组件，跟 M5 画布一样没法在无头环境里自动化端到端测试，这部分需要真实浏览器验证。

### 输入鲁棒性（`core/image_io.py`、`core/detectors/tiling.py`）—— 16 位 TIFF 被读成全白、大图悄悄检不出东西

排查"评委会用自己的图"时发现并修掉的三个问题，都是**不报错、只是结果不对**，最难察觉：

- **16位/浮点 TIFF 被读成全白或全黑。** 原来用 `Image.open(...).convert("RGB")`，对 `I;16` 模式是**截断**到255：一张0~60000的渐变图转出来**100%是白的**；0~1的浮点 TIFF 则几乎全黑。显微镜/探测器常输出这种格式。现在 `load_rgb()` 对高位深数据按 0.5~99.5 百分位拉伸到8位（几个热点像素不会压垮对比度，16位数据很少铺满量程），一并处理：灰度/RGBA/调色板/二值图、多页 TIFF 取第一页、损坏/截断/不是图像的文件给可读报错（不再抛一整页 traceback）、超过1亿像素拒绝。
- **大图悄悄漏检。** torchvision 检测模型会把输入缩放到短边800像素（长边≤1333）。用真实 BAM_TiO2 图拼成的大图实测（颗粒专用模型）：**1024×768 检出51个；2048×1536 只检出49个（应在200个上下）；4096×3072 检出0个**，没有任何提示。现在图像若会被缩到原尺寸的75%以下（1024×1024 的常见方图不受影响），就按800像素分块、重叠160像素，各块按质心归属的"核心区"去重后拼接。
  - **验证**：拼接结果在 2048×1536 上检出176个，无重复（IoU>0.5 的重复对=0）；在原图上强制分块（768px）与整图检测对比，47个分块实例全部与整图实例匹配（整图51个）。**这是自洽性检查，不是新的精度评估**——分块后在 BAM_TiO2 留出集上的召回/精确率没有重新测过。
  - **一个踩过的坑**：最后一块瓦片为了贴边会和前一块重叠更多，若每块各自从边缘缩进固定距离算核心区，核心区会重叠、同一个颗粒被报两次（强制分块测试里出现过53对重复）。改成相邻核心区在重叠区正中相接，保证精确划分；有单元测试，并用旧规则做过变异验证确实会失败。
  - **限制**：逐实例掩膜是 (N,H,W) 布尔堆，大图上颗粒很多时内存按 N×H×W 增长：4096×3072 上924个实例需要约11.6 GB，超过3 GB 上限时**拒绝并提示裁剪**，不会把机器拖进交换。裂纹模型同样分块，跨块的长裂纹会在块边界被切成几段，由原来的邻近合并再接起来。超过约160像素的大目标在块边界可能被截断。
- **报告图表依赖 Chrome（已加备用画法）**：`plotly` 导出图片用的 `kaleido` 1.x 需要本机装有 Chrome/Chromium，没有时直接抛 `ChromeNotFoundError`，"生成实验报告"就崩——换到评委的新机器上很可能遇到。`core/report.py::figure_png` 现在先试 plotly 导出，失败就用 matplotlib 按同样的数据重画直方图（样式更朴素；系统里没有中文字体时坐标轴文字自动退化为英文，避免显示成方框）。有 mock 掉导出的单元测试覆盖。
- **浏览器里实测**（真实上传）：损坏文件→"无法读取为图像文件"；同一张图转成16位 TIFF→检出50个（8位原图51个）；2048×1536→提示已分块、检出176个。

### 离线加载 Grounding-DINO

`ZeroShotDetector` 的文本编码器（`bert-base-uncased`）默认通过 HuggingFace Hub 加载，首次运行需要联网下载一次，之后会缓存在 `~/.cache/huggingface/hub/`。缓存好之后可以设置环境变量强制离线加载，跳过每次启动时的"检查更新"网络请求：

```bash
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
```

**注意**：开启离线模式后，如果缓存不存在（比如换了一台新机器、或清空过缓存），加载会直接报错而不是自动联网下载——这是更安全的失败方式，但意味着**新环境部署时必须先联网跑一次（不设置这两个环境变量）把模型缓存下载好，再切换到离线模式**。
